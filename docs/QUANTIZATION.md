# Кванты и деквант

Модель хранит веса в блочных форматах GGML. Горячий путь считает скалярное
произведение прямо по упакованным блокам; деквант в `float` нужен холодным
путям, эмбеддингам, `vcheck` и скалярному fallback.

Смежное: [KERNELS.md](KERNELS.md) — как блоки умножаются на активацию;
[GGUF.md](GGUF.md) — откуда берутся коды и размеры.

## 1. Геометрия блока

`BlockSpec` — это пара «сколько весов покрывает блок» и «сколько байт он
занимает»:

```cpp
struct BlockSpec {
  uint32_t weights = 0;
  uint32_t bytes = 0;
};
```

Размер строки:

```
row_bytes = in_dim / spec.weights * spec.bytes
```

`in_dim` обязан делиться на `spec.weights`. Для `Q8_0` это 32, для
K-квантов и IQ-квантов — 256. Проверка выполняется при загрузке, а не в
горячем цикле.

## 2. Поддерживаемые форматы

| тип | блок | байт | бит/вес | деквант | NEON dot |
|---|---:|---:|---:|---|---|
| `F32` | 1 | 4 | 32 | да | fallback |
| `F16` | 1 | 2 | 16 | да | fallback |
| `BF16` | 1 | 2 | 16 | да | fallback |
| `Q4_0` | 32 | 18 | 4.5 | да | да |
| `Q8_0` | 32 | 34 | 8.5 | да | да |
| `Q4_K` | 256 | 144 | 4.5 | да | fallback |
| `Q5_K` | 256 | 176 | 5.5 | да | fallback |
| `Q6_K` | 256 | 210 | 6.56 | да | fallback |
| `IQ2_S` | 256 | 82 | 2.56 | да | да |
| `IQ3_XXS` | 256 | 98 | 3.06 | да | да |
| `IQ3_S` | 256 | 110 | 3.44 | да | да |
| `IQ4_XS` | 256 | 136 | 4.25 | да | да |

В таблице перечислены форматы, которые реально читает рантайм. `QuantType`
знает больше кодов GGML (0…30), но `dequant_into` и ядра поддерживают только
этот набор; остальные возвращают `UnsupportedQuant`.

Коды 100…102 зарезервированы под экспериментальные форматы с группой 64 и в
горячем пути не используются.

## 3. Q8_0: 34 байта на 32 веса

Самый важный формат: в нём лежат attention, shared expert и плотные веса
после конвертации.

```
смещение  размер  поле
0         2       d, f16 scale
2         32      q[0..31], int8
```

Деквант:

```cpp
float d = f16_to_f32(read_u16(src, base));
for (int j = 0; j < 32; ++j) {
  out[y++] = d * static_cast<float>(static_cast<int8_t>(src[base + 2 + j]));
}
```

В горячем ядре `d` умножается на scale активации уже после `vdotq_s32`.
Активация квантуется в тот же блок 32: `int8` + `float` scale на блок.

## 4. Q4_0: 18 байт на 32 веса

```
0   2   d, f16 scale
2   16  qs[16], по два 4-битных веса в байте
```

Порядок распаковки: сначала младшие нибблы (`qs[j] & 0x0F`) для весов
`0..15`, затем старшие (`qs[j] >> 4`) для `16..31`; из каждого значения
вычитается 8.

```cpp
for (int j = 0; j < 16; ++j)
  out[y++] = float(int(src[base + 2 + j] & 0x0F) - 8) * d;
for (int j = 0; j < 16; ++j)
  out[y++] = float(int(src[base + 2 + j] >> 4) - 8) * d;
```

## 5. Q4_K / Q5_K / Q6_K

K-кванты — блок 256 весов и супер-блоки по 32. У них две шкалы: `d` для
значений и `dmin` для смещения (у `Q6_K` смещения нет).

### Q4_K, 144 байта

```
0    2    d, f16
2    2    dmin, f16
4    12   scales[12], 6-битные scale/min пары
16   128  qs, 4-битные веса
```

`get_scale_min_k4(j, scales)` собирает 6-битные `scale` и `min` из двух
байтов; младшие 4 бита лежат в одном месте, старшие 2 — в другом. Значение:
`d * scale * q - dmin * min`.

### Q5_K, 176 байт

```
0    2    d
2    2    dmin
4    12   scales
16   32   qh, старшие биты
48   128  qs, младшие 4 бита
```

Пятый бит берётся из `qh`, поэтому вес — 5-битное значение, а не 4-битное.

### Q6_K, 210 байт

```
0    128  ql, младшие 4 бита
128  64   qh, старшие 2 бита
192  16   scales, int8 на 16 групп
208  2    d, f16
```

Значение: `d * scales[group] * q`, где `q` — 6-битное число со знаком
(`-32..31`). Это самый точный из K-квантов в наборе.

## 6. IQ-кванты

IQ-форматы используют таблицы-решётки и отдельные знаки. Таблицы лежат в
`include/tokshit/gguf_tables.hpp` и скопированы без изменений:

| таблица | размер | где используется |
|---|---:|---|
| `iq2s_grid` | 1024 | `IQ2_S` |
| `iq3xxs_grid` | 256 | `IQ3_XXS` |
| `iq3s_grid` | 512 | `IQ3_S` |
| `kvalues_iq4nl` | 16 | `IQ4_XS` |
| `kmask_iq2xs`, `ksigns_iq2xs` | 8 / 128 | знаки IQ2 |

### IQ2_S, 82 байта

```
0   2    d, f16
2   64   qs: 32 индекса + 32 байта знаков
66  16   qh: по 2 бита на индекс
74  8    scales: 4-битные scale
```

Индекс в решётку: 10 бит, где младшие 8 — `qs`, старшие 2 — `qh`.
Знак берётся из `signs`. Вклад блока: `d * (0.5 + scale) * 0.25 * grid`.

### IQ3_XXS, 98 байт

```
0   2    d
2   64   qs: 8 байт на группу из 32 весов
66  32   scales_and_signs: 4 байта на группу
```

Младшие 8 бит индекса — `qs`, старшие 8 — из `scales_and_signs`; знаки
упакованы в тот же `aux32`.

### IQ3_S, 110 байт

```
0   2    d
2   64   qs
66  32   qh
74  32   signs
106 4    scales
```

Индекс — 9 бит: 8 из `qs`, девятый из `qh`. Scale — 4 бита, значение
`d * (1 + 2 * scale)`. Знаки лежат отдельным слоем по 32 байта.

### IQ4_XS, 136 байт

```
0   2    d
2   2    scales_h
4   4    scales_l
8   128  qs: по два 4-битных индекса в байте
```

Scale группы: младшие 4 бита из `scales_l`, старшие 2 — из `scales_h`;
значение `d * (scale - 32)`. 4-битный индекс смотрит в `kvalues_iq4nl[16]`.
В коде это `dequant_iq4_xs` и `neon::dot_iq4xs`.

> Точные битовые операции для IQ-квантов лучше читать в `src/dequant.cpp`:
> там порядок циклов совпадает с эталоном, а таблицы — в
> `gguf_tables.hpp`. Формулы выше задают смысл, не заменяют код.

## 7. Переквантование плотных весов в Q8_0

У `Q5_K`, `Q6_K` и `BF16` нет NEON-ядра. Скалярный путь для них — деквант в
`float` плюс dot, это 1–1.6 ГБ/с против 30+ ГБ/с у `Q8_0`. Поэтому при
загрузке горячие плотные тензоры конвертируются в `Q8_0`.

```text
TOKSHIT_HOT_CONV=1  (по умолчанию) — конвертировать
TOKSHIT_HOT_CONV=0                — оставить исходный квант
```

Что конвертируется: только тензоры из `collect_hot()` (attention q/k/v/o,
плотный FFN, shared expert, роутер, `output.weight`), только если для
исходного кванта нет NEON-ядра и `in_dim % 32 == 0`.

Цена: примерно +1.5 бита на вес и ~0.6 ГБ памяти на модели Flint. Выигрыш:
плотный matvec переходит на Q8_0-ядро.

### Измеренный A/B

Одиночные шумные прогоны на целевом телефоне:

| метрика | `HOT_CONV=0` | `HOT_CONV=1` |
|---|---:|---:|
| matvec, ГБ/с | 5.47 | 9.15 |
| полный декод, tok/s | 1.90 | 2.28 |
| hot-веса, МБ | 1626 | 1740 |

Цифры одиночные и шумные: телефон троттлит, а полный декод упирается в
диск. Для сравнения конфигов нужен `scripts/ab.sh`.

## 8. f16 / bf16

`f16_to_f32` использует аппаратное преобразование на aarch64, а на остальных
платформах — программное с медленным путём для субнормалей, NaN и Inf.
`f32_to_f16` округляет к ближайшему чётному.

`BF16` — это старшие 16 бит `float`: `bits << 16`. Отдельной точности не
добавляет, зато не требует таблиц.

## 9. Численные заметки

- `-ffast-math` не включается: он меняет `exp`/`softmax` и ломает
  паритет логитов.
- Порядок обхода блоков и распаковки нибблов — часть формата. Менять его
  можно только вместе с `vcheck`.
- NEON-ядро обязано совпадать со скалярным деквантом в пределах `1e-3` на
  реальных блоках.
- `vcheck` проверяет деквант всех используемых квантов на реальном GGUF.
- Логиты сравниваются отдельно: расхождение в декванте может быть незаметно
  в тексте, но видно в `--dump-logits`.

