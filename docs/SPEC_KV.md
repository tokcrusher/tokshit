# KV-кеш, батч-матвек и спекулятивный цикл

Как устроены `kv.hpp`, `batch.hpp`, `attn_batch.hpp` и `spec_loop.hpp`,
что проверено и какие ограничения остаются.

## 1. Зачем батчинг

Одиночный декод упирается в плотные веса: 1.74 ГБ на токен. При 12.6 ГБ/с
это 138 мс, около 7 tok/s до учёта экспертов. Батчинг и спекуляция читают
плотные веса реже, чем раз на токен, но требуют KV-кеша фиксированной
ёмкости.

## 2. KV-кеш

`include/tokshit/kv.hpp`, `src/kv.cpp`.

- Два сплошных сляба `k` и `v`; слой `l` начинается с `l * cap * stride`.
- `stride = kv_dim * (f16 ? 2 : 4)` байт; `kv_dim = n_kv_heads * head_dim`
  (у Flint 4 × 128 = 512).
- Позиции абсолютные, строки перезаписываемые. `truncate_all(n)` откатывает
  кэш без пересылок.
- f16 по умолчанию: 2К контекста — около 195 МБ на k+v, f32 вдвое дороже.
  Attention читает весь K/V на каждый токен, поэтому полоса важнее
  точности.

## 3. Батч-матвек

`include/tokshit/batch.hpp`, `src/compute/kernels_batch.cpp`.

`BatchSeg` — прямоугольник весов (`rows × in_dim`) плюс `b` активаций.
`batchlib::run_bsegs` режет сегменты на задачи «пачка строк × все b
активаций» и отправляет их в общий пул. Строка весов остаётся в L1 на время
b проходов, поэтому DRAM-трафик на выход делится примерно на b.

Батч-путь использует `kernels::dot_row`, поэтому семантика совпадает со
скалярным путём. Отдельные batched-ядра можно добавить без изменения API.

## 4. Attention батчем

`include/tokshit/attn_batch.hpp`, `src/compute/attn_batch.cpp`.

`attend_row` считает одну строку батча: scores по `[start, end)`, softmax с
sink (sink только в знаменателе, в V-сумму не входит), взвешенная сумма V.
Обход вложен по kv-головам: K/V-сегмент читается один раз на группу из
`group = n_heads / n_kvh` q-голов. На 2К это главная экономия полосы.

- `first` — абсолютная позиция строки 0; строка `j` видит `[.., first+j]`.
- `win[j]` — начало sliding-window; `cap` не даёт выйти за сляб.
- f16 и f32 сверяются с наивной скалярной ссылкой, включая sink и окно.

## 5. Спекуляция

`include/tokshit/spec_loop.hpp`, `src/spec_loop.cpp`.

Раунд: `draft → verify → accept → truncate`.

1. Черновик: первый токен берётся из головы прошлого раунда, следующие
   `K-1` генерит батч из одного токена с урезанным роутером
   (`TOKSHIT_DRAFT_TOPK`).
2. Verify: те же кандидаты прогоняются батчем с полным роутером; KV
   перезаписывает их строки.
3. Цепочка: `argmax(row j)` должен совпасть с `cand[j+1]`; принимается
   минимум один токен. Логиты последнего принятого — голова следующего
   раунда.
4. `kv.truncate_all(pos)` выбрасывает непринятый хвост.

Только жадный семплинг. При greedy выход обязан совпадать с обычным
декодом, иначе это не lossless-спекуляция. Ручки: `TOKSHIT_SPEC`,
`TOKSHIT_SPEC_K`, `TOKSHIT_DRAFT_TOPK`, `TOKSHIT_SPEC_VERIFY_TOPK`,
`TOKSHIT_SPEC_CTX`, `TOKSHIT_SPEC_MAXB`. `--spec-fast` и
`--spec-verify-topk` меняют выход модели и помечаются **LOSSY**.

## 6. Что проверено

- KV: capacity, high-water, rollback, f16/f32 roundtrip.
- Attention: f16/f32 против скалярной ссылки, sink и SWA.
- Деквант Q8_0 и `dot_row_multi` на нескольких активациях.
- Batched matvec против `dot_row` для F32 и Q8_0.
- 161 кейс / 7715 проверок зелёные локально.
- Паритет на устройстве: greedy-иды `--spec` и обычного декода совпали
  байт в байт на коротких промптах.

## 7. Замеры

| режим | tok/s | принято |
|---|---:|---:|
| plain greedy, top-6 | 2.40 | — |
| `--spec --spec-k 3`, полный verify | 0.93–1.00 | 50–78 % |
| `--spec-fast`, verify top-2 | 2.09 | 83 % |
| `--turbo`, top-2 + Q4_0 | 3.52 | — |

Спекуляция расширяет union экспертов verify-батча примерно во столько же
раз, во сколько батч экономит плотные веса. На коротких сериях выигрыша
нет. Полный verify остаётся lossless, но на этом устройстве медленнее
обычного декода.

## 8. Ограничения

- Батч-путь зовёт `dot_row` построчно; batched NEON-ядра — следующий шаг.
- Контекст длиннее sliding-window (513) требует отдельной проверки
  батчевого SWA-пути.
- Пиннинг горячих экспертов удерживает только рабочий набор; оценивать
  выигрыш нужно на длинном прогоне, а не по теоретической вилке.

## 9. Ручки

| ручка | что делает |
|---|---|
| `--spec-verify-topk N` | top-k на verify; меньше union экспертов (LOSSY) |
| `--pin-experts N` | пин N частых экспертов на слой после префилла |
| `--expert-stats` | union экспертов и hit-rate кэша |
| `--mlock` | зарезервировано, не подключено |
| `--turbo` | **LOSSY**: top-2 + Q4_0 dense, кэш 1024, O_DIRECT |
| `--spec-fast` | **LOSSY**: `--spec --spec-k 4 --spec-maxb 8 --spec-verify-topk 2` |

Внутри также: `dot_row_multi` раскладывает строку весов в float один раз
для всех активаций батча; батч-путь не аллоцирует память на каждом слое
(`segs`, `idx` и пары эксперт-строка переиспользуются).
