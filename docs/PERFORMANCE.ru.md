# производительность (ru)

Здесь измеренные цифры и выводы. Всё снято на одном телефоне
(8 ядер: 1× Cortex-X4 + 7× Cortex-A720, 15.2 ГБ RAM, Android/Termux).
Модель — `flint-UD-Q3_K_XL.gguf`, 18.49 ГБ. Числа шумные: телефон троттлит,
фоновая активность и температура меняют результат на десятки процентов.
Текущий baseline и план сессии 16.11.2026 — в
[PERF_SESSION2.md](PERF_SESSION2.md).

## коротко

| вопрос | ответ |
|---|---|
| обычный декод top-6, кэш 512 МБ (текущая сессия) | **1.1–1.9 tok/s** |
| тот же конфиг, ранние длинные прогоны | 2.0–2.7 tok/s (исторический) |
| без кэша, mmap (исторический) | 1.24–1.37 tok/s |
| кэш 2–3 ГБ (исторический) | ~2.05 tok/s, память уходит в reclaim |
| `--fast` (исторический) | 4.52 tok/s, но **lossy top-2** |
| спекуляция, полный verify | 0.93–1.00 tok/s, acceptance 50–78 % |
| батчевый префилл | 4–5.3 tok/s (`TOKSHIT_PREFILL_BATCH=32`) |
| AHB | 5.2 GB/s на потоке; убирает ZRAM/swap |

## методика

- Только `scripts/safe_run.sh`: он раз в секунду проверяет `MemAvailable` и
  убивает процесс ниже `TOKSHIT_MIN_AVAIL_MB` (по умолчанию 1200). Иначе
  легко получить LMK и потерять ssh.
- 12–24 новых токена на прогон, `--temperature 0` для повторяемости.
- Конфиги сравниваются вперемешку в одной сессии (`scripts/ab.sh`), а не
  последовательными одиночными прогонами: температура и троттлинг дрейфуют.
- «Холодный» кэш — сразу после загрузки, без прогрева экспертов.
  «Тёплый page cache» — модель уже читалась, файл лежит в page cache
  настолько, насколько позволяет RAM.
- `--fast` и `--spec-*` помечены как **lossy**: они меняют выход модели
  (top-2 вместо top-6), поэтому их нельзя ставить в один ряд с обычным
  декодом.
- Микробенчмарки (`kbench`, `bwbench`, `ahbtest`) измеряют отдельные
  участки и **не** предсказывают tok/s полного декода.

Связанные документы: [RUNTIME.md](RUNTIME.md) — как устроен поток;
[KERNELS.md](KERNELS.md) — ядра и полоса; [ROADMAP.md](ROADMAP.md) — что
делать дальше.

## точные команды

Обычный декод с кэшем 512 МБ:

```sh
scripts/safe_run.sh build/tokshit --temperature 0 --cache-mb 512 \
  --expert-stats ~/models/flint-UD-Q3_K_XL.gguf "hi" 24
```

Без кэша (mmap):

```sh
scripts/safe_run.sh build/tokshit --temperature 0 --cache-mb 0 \
  --expert-stats ~/models/flint-UD-Q3_K_XL.gguf "hi" 24
```

Кэш 2 ГБ:

```sh
scripts/safe_run.sh build/tokshit --temperature 0 --cache-mb 2048 \
  --expert-stats ~/models/flint-UD-Q3_K_XL.gguf "hi" 24
```

Lossy-пресет:

```sh
scripts/safe_run.sh build/tokshit --fast \
  ~/models/flint-UD-Q3_K_XL.gguf "hi" 24
```

Спекуляция, полный verify:

```sh
scripts/safe_run.sh build/tokshit --temperature 0 --cache-mb 512 \
  --spec --spec-k 3 ~/models/flint-UD-Q3_K_XL.gguf "hi" 24
```

Спекуляция, verify top-2 (lossy):

```sh
scripts/safe_run.sh build/tokshit --temperature 0 --cache-mb 512 \
  --spec --spec-k 3 --spec-verify-topk 2 \
  ~/models/flint-UD-Q3_K_XL.gguf "hi" 24
```

`--spec-fast`:

```sh
scripts/safe_run.sh build/tokshit --spec-fast \
  ~/models/flint-UD-Q3_K_XL.gguf "hi" 24
```

Разбивка по фазам и I/O:

```sh
GGUF_TIME=1 scripts/safe_run.sh build/tokshit --temperature 0 --cache-mb 512 \
  --expert-stats ~/models/flint-UD-Q3_K_XL.gguf "hi" 24
```

Микробенчмарки:

```sh
# один тензор, 20 итераций
build/kbench ~/models/flint-UD-Q3_K_XL.gguf 20 blk.2.attn_q.weight

# чтение 2 ГБ из page cache
build/bwbench ~/models/flint-UD-Q3_K_XL.gguf 2048 3

# AHB против malloc на блоках 328/576 КБ
scripts/safe_run.sh build/ahbtest --mb 1024 --blocks 256

# matvec по attention-тензорам всей модели
GGUF_TIME=1 scripts/safe_run.sh build/tokshit --bench-mm \
  ~/models/flint-UD-Q3_K_XL.gguf
```

Сравнение `AHB_USAGE`:

```sh
TOKSHIT_AHB_USAGE=rare  GGUF_TIME=1 scripts/safe_run.sh build/tokshit ...
TOKSHIT_AHB_USAGE=often GGUF_TIME=1 scripts/safe_run.sh build/tokshit ...
```

Смотреть строку `[matvec: ... GB/s]`.

## результаты декода

| режим | кэш | I/O | tok/s | hit-rate | статус |
|---|---:|---|---:|---:|---|
| top-6 | 512 МБ | `O_DIRECT` | 1.1–1.9 | — | текущая сессия |
| top-6 | 0 | mmap | 1.24–1.37 | — | исторический |
| top-6 | 512 МБ | `O_DIRECT` | 2.0–2.7 | ~32 % | исторические длинные прогоны |
| top-6 | 2048 МБ | `O_DIRECT` | ~2.05 | ~40 % | исторический |
| top-6 | 3072 МБ | `O_DIRECT` | ~2.05 | ~40 % | исторический |
| top-2 | 0 | buffered | 4.52 | — | **lossy** (`--fast`), исторический |

Текущий baseline — 1.1–1.9 tok/s на обычном top-6 с кэшем 512 МБ. Диапазон
2.0–2.7 — лучший длинный прогон прошлых сессий; это исторический ориентир,
а не текущий baseline. Температура, фоновая нагрузка и ревизия кода
отличаются, поэтому смешивать диапазоны нельзя.

В исторических длинных прогонах кэш 512 МБ давал заметный выигрыш к mmap.
2–3 ГБ добавляют ~8 п.п. попаданий, но **не** tok/s: плотные веса и
reclaim съедают выигрыш, а 3–4 ГБ на 15-гигабайтном телефоне легко
приводят к OOM. 4.52 tok/s у `--fast` — это top-2 из 6, другой режим, не
«обычный декод».

## результаты спекуляции

| режим | verify | tok/s | принято | статус |
|---|---|---:|---:|---|
| `--spec --spec-k 3` | полный | 0.93–1.00 | 50–78 % | lossless, паритет greedy подтверждён |
| `--spec --spec-k 3 --spec-verify-topk 2` | top-2 | ~1.5 | ~50 % | **lossy** |
| `--spec-fast` | top-2 | 2.09 | 83 % | **lossy** |

Полный verify lossless: acceptance 50–78 % на промптах до ~500 токенов, ids
совпадают с обычным greedy байт в байт. Ранние нули в этой таблице не
воспроизводятся (см. [SPEC_KV.md](SPEC_KV.md)); метрики `expert_hit/miss`
теперь считаются и в батчевом пути.

## исторические прогоны

Таблица ниже — ранние замеры на другом наборе весов и с другими настройками
кэша. Они шумные и не сравнимы с текущей рабочей точкой 512 МБ; оставлены

| конфиг | tok/s |
|---|---:|
| cache=0 | 1.40 |
| cache=1000 + prefetch, workers=8 | 1.74 |
| cache=4000 | 1.54 |
| `TOKSHIT_HOT=1`, cache=1500 | 1.56 |
| cache=1000 + prefetch, workers=6 | 2.0–2.2 |
| cache=512, `O_DIRECT` | 2.0–2.7 |
| cache=2048/3072, `O_DIRECT` | ~2.05 |

Короткие прогоны (`GGUF_NLAYERS`) показывают потолок ядер и пула:

| слоёв | tok/s | matvec |
|---:|---:|---:|
| 4 | 24 | 25.4 GB/s |
| 8 | 12 | 25.8 GB/s |
| 16 | — | 22–26 GB/s |
| 47 | — | 7–8 GB/s |

На 47 слоях те же ядра дают 7–8 GB/s при `TOKSHIT_HOT=1`: веса уже в RAM,
значит дело не в page cache, а в конкуренции с потоком экспертов и
накладных расходах полного прохода. Дальнейшая оптимизация отдельных ядер
на tok/s почти не влияет.

## эксперты через pread

Раньше промах кэша копировал данные из mmap в `std::vector`: сначала page
fault, потом `memcpy`. Теперь `Gguf::read_at` читает прямо в буфер кэша, а
`TOKSHIT_FADV_DONTNEED=1` дополнительно роняет page cache диапазона.

Замер (cache=1000, prefetch, workers=6):

| вариант | tok/s | RSS | majflt | read_bytes |
|---|---:|---:|---:|---:|
| mmap-копия | 2.04–2.19 | ~6000 MB | ~11000 | ~9 GB |
| pread | 2.06 | 2587 MB | 387 | 5.69 GB |
| pread + fadvise | 2.18 | 2634 MB | 4 | 4.87 GB |

Скорость в пределах шума, RSS упал на ~3.4 ГБ, major faults — почти в ноль.
`TOKSHIT_FADV_DONTNEED` по умолчанию выключен.

## фоновые читатели

`ExpertIo` выносит чтение экспертов из счётного потока:

- две очереди: спрос и предсказание; спрос всегда первым;
- `inflight_` дедуплицирует чтение одного блока;
- `new_epoch()` на каждом токене выбрасывает устаревшие предсказания;
- предсказание — `freq_->last[layer]`, то есть эксперты, выбранные роутером
  на прошлом токене; заказ идёт на 1–2 слоя вперёд, пока считается
  attention;
- в MoE-блоке заказываются все 24 чтения слоя: сначала gate/up, потом down;
- `O_DIRECT` не даёт экспертным байтам вытеснять плотные веса из page
  cache; при отказе платформы чтение становится буферизованным;
- окно чтения выравнивается по `st_blksize`, хвост копируется из
  bounce-буфера.

На телефоне prefetch по прошлому токену даёт ~38 % попаданий, но удваивает
поток с диска и примерно вдвое замедляет декод. Поэтому по умолчанию
выключен.

## ранние замеры acceptance

До текущей серии замеров acceptance проверялся отдельно, на 48 id, cache
4000, жадный декод:

| draft | принято | первая серия | серий | средняя серия |
|---|---:|---:|---:|---:|
| top-1 | 6/48 = 12.5 % | 1 | 5 | 1.20 |
| top-2 | 35/48 = 72.9 % | 2 | 12 | 2.92 |

Скорость в той же сессии: полный декод 2.18 tok/s; teacher-forced draft в
verify-режиме — 2.67 шага/с (top-2) и 2.33 (top-1); полный прогон читает
~200 МБ/токен. Top-2 — рабочий вариант; top-1 даёт почти нулевой
acceptance. Полный verify в спекуляции даёт 50–78 % принятых на промптах
до ~500 токенов; открытый пункт один — батч-путь на контексте длиннее
sliding-window (513), см. [ROADMAP.md](ROADMAP.md).

## бюджет на токен

Плотные веса, которые читаются на каждом токене:

```
attention q/k/v/o          849 МБ
shared expert              267 МБ
dense ffn + router         124 МБ
output.weight              312 МБ
------------------------------------
итого                     ~1551 МБ
```

Эмбеддинг читается одной строкой (~2 КБ), norm-векторы — килобайты, их можно
не считать.

Эксперты при полном промахе:

```
15.77 ГБ всех экспертов / 256 × 6 = 0.370 ГБ/токен
```

При hit-rate 32 % остаётся ~0.252 ГБ, при 40 % — ~0.222 ГБ.

Итого на токен при кэше 512 МБ: `1.551 + 0.252 ≈ 1.80 ГБ`. Для
исторического прогона 2.35 tok/s это ~0.43 с/токен и ~4.2 GB/s суммарно.
Текущая сессия даёт 1.1–1.9 tok/s, то есть примерно 2.0–3.4 GB/s суммарно;
причина расхождения пока не локализована.

## где уходит время

### плотные веса и AHB

Плотные веса — 1.55 ГБ на токен, это самая большая статья. Микробенч
показывает 25–35 GB/s на отдельных сегментах, но полный поток по 391
буферу даёт 5.21 GB/s (`rare`). При 5.21 GB/s только плотные веса стоят
~0.30 с/токен, то есть потолок ~3.3 tok/s ещё до чтения экспертов.
Текущие 1.1–1.9 tok/s ниже этого потолка: остальное добавляют I/O
экспертов, attention и планировщик.

Почему 391 буфер: gralloc отвергает один буфер на 1.55 ГБ (`rc=-129`).
Разбиение на тензоры спасает от отказа, но стоит TLB/непрерывности.

`often` на этом устройстве даёт некэшируемый mapping: 3.10 GB/s, поэтому
дефолт — `rare`. `TOKSHIT_AHB=0` уводит всё в malloc: память освобождается,
но ZRAM начинает свопить, и задержки растут.

Переквантование плотных весов без NEON-ядра в `Q8_0`
(`TOKSHIT_HOT_CONV=1`, по умолчанию) поднимает matvec с 5.47 до 9.15 GB/s,
полный декод — с 1.90 до 2.28 tok/s, hot-веса растут с 1626 до 1740 МБ.
Это исторический A/B на одной ревизии кода: текущий baseline ниже, поэтому
таблица показывает эффект конверсии, а не абсолютную скорость. Оговорки —
в [QUANTIZATION.md](QUANTIZATION.md).

### эксперты и диск

Сырое чтение с флеша — ~1.4 GB/s. При 32 % попаданий нужно прочитать
~0.25 ГБ, это ~180 мс. Экспертный matvec упирается не в CPU, а в ожидание
страниц: при `cache 0` 12 проходов занимают 7–9 с, то есть 0.6–0.75 с на
токен. Это и есть исторические 1.24–1.37 tok/s.

`O_DIRECT` не ускоряет сам диск, но не даёт экспертам вытеснять плотные веса
из page cache. Поэтому в исторических длинных прогонах с кэшем 512 МБ
получалось 2.0–2.7, а не 1.3; текущая сессия даёт 1.1–1.9.

### пул

Пул не является главным узким местом: на коротких прогонах (4–8 слоёв)
получается 12–24 tok/s и 25+ GB/s. В полном прогоне `GGUF_TIME=1` показывает
`load` и `downwait` — это ожидание экспертов, а не барьер пула. Если
`downwait` большой, диск не успевает; если `load` большой — кэш промахивается.

### спекуляция

Verify-батч из `b` строк расширяет union экспертов примерно в `b` раз.
Плотные веса действительно переиспользуются, но эксперты — нет: у каждого
токена свой top-6. На коротких сериях принятых токенов эффект нейтральный.
Плюс открытые баги с acceptance и счётчиками кэша.

## почему 5 tok/s не получается

5 tok/s — это 200 мс на токен. Расклад:

| статья | при 5 tok/s |
|---|---|
| плотные 1.551 ГБ | нужно ≥ 7.8 GB/s только на них |
| эксперты 0.25 ГБ | ещё ~180 мс при 1.4 GB/s |
| итого | уже > 380 мс |

Даже если эксперты станут бесплатными, для 200 мс нужен поток плотных весов
~7.8 GB/s. Сейчас полный AHB-поток — 5.21 GB/s. Исторический `--fast`
(top-2, тёплый page cache) вытягивает 4.52 tok/s, то есть ~7.0 GB/s
эффективно, но это lossy-режим.

Текущий путь с полным top-6 упирается в поток плотных весов и чтение
экспертов; 5 tok/s требует другого баланса. Варианты: ускорить поток
плотных весов (непрерывная память, меньше буферов, другой pinning),
поднять hit-rate кэша экспертов или использовать lossy-режим. Цель 5 tok/s
остаётся в работе; конкретные шаги — в [ROADMAP.md](ROADMAP.md).

## что пробовать дальше

Сначала воспроизвести текущий baseline 1.1–1.9 и исторический 2.0–2.7
вперемешку в одной сессии. Без этого нельзя отделить троттлинг и состояние
кода от эффекта ядра или кэша.

1. **Локализовать SWA-баг батч-пути.** Батчевый prefill ломается на
   контексте длиннее sliding-window (513). Метрики `expert_hit/miss` в
   батчевом пути уже считаются; acceptance на полном verify измерен
   (50–78 %), остаётся баг длинного контекста.
2. **Ускорить поток плотных весов.** Сравнить: 391 AHB-буфер, один большой
   malloc, `mlock`, `TOKSHIT_HOT=0`. Цель — понять, где теряются 25–35 GB/s:
   в AHB, в разбиении или в самом полном прогоне.
3. **Проверить `TOKSHIT_HOT=0` + AHB только для кэша.** Возможно, плотные
   веса в page cache быстрее, чем 391 dma-buf.
4. **Заказывать down-эксперты раньше.** Сейчас gate/up читаются, потом down
   после swiglu; если диск простаивает, можно отправить все 24 чтения сразу.
5. **Уменьшить трафик плотных весов без потери качества.** Например,
   квантовать `output.weight` агрессивнее — но это меняет выход, нужен
   паритетный гейт.
6. **Не оптимизировать ядра по микробенчу.** 25–35 GB/s на сегментах уже
   есть; полный декод упирается в поток памяти и диск.
7. **Сравнивать только вперемешку.** `scripts/ab.sh` и `scripts/sweep.sh`
   для этого и существуют.

## правила замеров

- Не ставить кэш 3–4 ГБ «на всякий случай»: reclaim и OOM.
- Не включать `--prefetch`: на этом телефоне ~2x медленнее.
- Не включать `--fadv-dontneed` без замера: можно выкинуть нужные страницы.
- Не ставить `TOKSHIT_AHB_USAGE=often`: медленнее.
- Не запускать два процесса модели одновременно: 18.49 ГБ и общий AHB-бюджет.
- `--fast` сравнивать только с другими lossy-режимами: это top-2.
- Числа обычного декода указывать только по полному top-6, не по `--fast`
  или микробенчмаркам.
- Не смешивать сессии: текущий baseline — 1.1–1.9 tok/s, исторический
  длинный прогон — 2.0–2.7 tok/s.

## открытые баги и вопросы

1. Батч-путь ломается на контексте длиннее sliding-window (513): prefill
   ~1040-токенного промпта даёт взорванные логиты и мусорный декод. На
   коротких промптах путь корректен. Главный открытый баг спекуляции.
